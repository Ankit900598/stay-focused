## Incident summary, as given

Xiaomi 2312DRAABI, tester APK `BF0A101A…` (commit `39f130c`), backend confirms `promise_compiler_v09` on build `8ed37e46…`. `PhoneCodex Accessibility` shows enabled in Settings, but `dumpsys accessibility` lists it under **Crashed services** with no live PID. `ApplicationExitInfo` shows a system kill at 2026-09-28 13:33:57 IST with description `"OneKeyClean"`; an earlier exit was `"SwipeUpClean"`. ## 1. Does Android normally rebind an AccessibilityService after its process is killed? What may Xiaomi/MIUI change?

**Official source:** Android's own accessibility-service guide states the service lifecycle is "managed exclusively by the system" and that starting/stopping is "triggered exclusively by an explicit user action through enabling or disabling it in the device settings" (developer.android.com, *Create an accessibility service*). This is the load-bearing fact: **there is no documented, general Android guarantee that a killed accessibility service's process is automatically respawned and rebound** — the system *may* rebind it (as it does for many bound services when memory pressure clears and the client — here, `AccessibilityManagerService` — re-requests the binding), but this is not a stated contract, and AOSP's binding lifecycle explicitly has a terminal **failure** state.

**Community-documented (cross-referenced across multiple independent third-party reports, not an official Google statement):** `dumpsys accessibility` exposes four service buckets — *Enabled services*, *Binding services*, *Bound services*, and *Crashed services*. Multiple independent third-party investigations (a mobile-automation project's own bug tracker, cross-checked across several separate issues over time) describe the same mechanism: once a service's binding dies, `AccessibilityManagerService` records the component as **crashed** and **does not automatically retry** — the service stays enabled-but-crashed indefinitely until the user (or something acting as the user, via Settings) toggles the accessibility row off and back on. This matches the observed phone state exactly: enabled in Settings, present in *Crashed services*, absent PID, no automatic recovery.

**What Xiaomi/MIUI adds on top (Community-documented):** MIUI ships its own aggressive process-management layer distinct from stock AOSP's Low Memory Killer — battery-saver "background app freezing," an "Autostart" permission gate (MIUI 14+) that must be separately granted per app, and one-tap cleanup utilities in the Security app / recents UI. The observed `ApplicationExitInfo` descriptions **"OneKeyClean"** and **"SwipeUpClean"** are MIUI's own cleanup-utility labels — a third-party bug report against a different app on MIUI 13 shows the identical pattern (`REASON_OTHER`, description `"OneKeyClean"`, foreground-service importance) killing an app with no crash. This is a **documented, recurring MIUI behavior**, not unique to Strlix, and not a Java-level bug in Strlix's own code — it is an OS-vendor-initiated kill.

## 2. Which app-side recovery and truthful status reporting are Android-supported and Play-compliant? What requires the user to change MIUI settings?

**Android-supported, app-side (no MIUI setting needed):**
- **Truthful status reporting** — reading `dumpsys`-equivalent liveness via a heartbeat/lease the service itself writes while alive, and computing "alive" as *fresh lease age*, never as a cached boolean or as "Settings says enabled." This is standard, no special permission, fully Play-compliant. Strlix already does this — see §3.
- **Prompting the user to re-open Settings and toggle Accessibility back on** — Android provides no API for an app to programmatically re-enable its own accessibility service (confirmed by the same official source in §1: enabling is an explicit user action by design, for security reasons — an app silently re-enabling its own screen-reading/input-injection capability would be exactly the kind of thing this restriction exists to prevent). The only compliant app-side action is to detect the crashed/dead state and **ask the user to do it**, with a direct deep link to the Accessibility settings screen (`Settings.ACTION_ACCESSIBILITY_SETTINGS`) — standard, documented, already how "Turn on Accessibility"-style CTAs work industry-wide.
- **Play policy boundary (Official source, support.google.com/googleplay/android-developer, *Use of the AccessibilityService API*):** Play now enforces that Accessibility API usage which lets an app "autonomously initiate, plan, and execute actions" is restricted unless the app is a declared, genuine accessibility tool (`isAccessibilityTool="true"`) serving people with disabilities (screen readers, switch access, etc.), with stricter review from **28 January 2026**. **This is a real, separate compliance question for Strlix, not just a kill/rebind question:** Strlix uses the Accessibility API to read screens and drive blocking/overlay behavior for self-control/parental-style enforcement — this is not the traditional disability-accessibility use case the exemption describes. Any recovery design that leans *harder* on the Accessibility API (rather than working around its absence) increases exposure to this policy, independent of whether MIUI is killing the process. **Flagging this for product/legal awareness — it is outside this diagnosis's scope to resolve, but it is directly relevant to "what's Play-compliant" and should not be decided by engineering alone.**

**Requires the user to change an MIUI setting (cannot be done by the app):**
- Granting **Autostart** for the app (MIUI 14+ setting).
- Setting **Battery Saver / App Battery Saver** to "No restrictions" for the app.
- **Locking** the app in the Recents/multitask view (a MIUI-specific gesture — dragging the card down, or via the Security app's Boost Speed screen) so `SwipeUpClean` skips it.
- None of these are things `RECEIVE_BOOT_COMPLETED` or any other standard permission grants automatic control over — they are OEM UI toggles the user must set themselves. An app can *link* the user to the relevant settings screen (where a documented Xiaomi intent exists) but cannot set them programmatically. **This is Community-documented** (dontkillmyapp.com's Xiaomi page, a widely-cited crowd-sourced reference for OEM background-kill behavior — not an official Xiaomi document, and its exact menu wording/paths vary by MIUI version, so treat as directionally reliable, not verbatim-accurate for 2026's exact MIUI build).

## 3. How should Strlix avoid showing "Protected" when the AccessibilityService is enabled but not bound/alive? — Confirmed: already built correctly, with one bounded, inherent gap

**Confirmed by reading the code, not assumed:** Strlix already separates "enabled" from "alive," and already computes "alive" as a freshness check, not a cached flag:
- `AccessibilityHealthChecker.isPhoneCodexAccessibilityEnabled()` (`app/.../accessibility/AccessibilityHealthChecker.kt:13-19`) reads `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` — this is exactly the signal that stays "enabled" even while the service sits in *Crashed services* (§1) — it reflects the user's toggle, not live binding state.
- `RuntimeDiagStore.getHeartbeat()` (`app/.../data/RuntimeDiagStore.kt:82-94`) computes `serviceAlive` **freshly at read time**: `prefs.getBoolean(KEY_A11Y_ALIVE, false) && AccessibilityHeartbeatLaw.isServiceLeaseFresh(nowElapsedMillis = SystemClock.elapsedRealtime(), lastLeaseElapsedMillis = ...)`. `SystemClock.elapsedRealtime()` is boot-relative and keeps advancing even after the accessibility process dies (it only resets on a full device reboot), so a stale lease is correctly detected as stale on the very next read, from any process (this store is explicitly documented as "cross-process diagnostics," `RuntimeDiagStore.kt:14-15`) — not just by the (now-dead) service itself.
- `ProtectionReliabilityGate.evaluate()` (`app/.../domain/protection/ProtectionReliabilityGate.kt:85-98`) computes `loopAlive = input.accessibilityEnabled && input.accessibilityAlive` and returns `NOT_PROTECTING` with the exact copy *"PhoneCodex Accessibility is enabled but not connected. Phone rules are not being enforced."* whenever `loopAlive` is false — this is precisely the "enabled but not bound/alive → do not say Protected" behavior the question asks for, and it is already implemented, not a gap to design from scratch.

**The one real, bounded, inherent gap (Confirmed by reading the constants, not a code defect):** `AccessibilityHeartbeatLaw.SERVICE_LEASE_MAX_AGE_MS = 30_000L` (`app/.../domain/protection/AccessibilityHeartbeatLaw.kt:12`). This means there is an unavoidable **0-30 second window immediately after a kill** during which the last-written lease is still "fresh" by the clock, so a status read *during that exact window* would still say Protected even though the process just died. This is not a bug — it is the inherent latency of any heartbeat/lease-based liveness signal (you cannot detect death faster than your polling/lease interval without an OS-level death callback, which Android does not expose to third-party apps for other apps' processes, let alone gracefully for a service's own death). **The correct, honest characterization for product: "truthful within ~30 seconds of a kill," not "instantly truthful."** If a tighter bound is wanted, the lever is lowering `SERVICE_LEASE_MAX_AGE_MS` (a pure trade against how often the live service must write a lease, i.e., more `SharedPreferences.apply()` writes) — a tuning decision, not a new mechanism, and out of scope to recommend a specific new value without product input on the acceptable write-frequency cost.

## 5. Confirmed facts vs. hypotheses, restated for clarity

**Confirmed (this repo's code, read directly):** Strlix already separates "enabled" from "alive" (§3); the alive-check is freshness-based and cross-process-readable; the 30-second lease-age bound is a real, inherent, bounded staleness window, not an unbounded bug.

**Official source (Android/Google documentation):** accessibility-service enable/disable is an explicit-user-action-only lifecycle with no app-side programmatic re-enable path; Play's Accessibility API policy restricts autonomous-action usage with a 28 Jan 2026 enforcement date and an `isAccessibilityTool` exemption for genuine disability-accessibility tools.

**Community-documented (cross-referenced third-party sources, explicitly not an official vendor statement):** the *Bound / Binding / Crashed services* taxonomy and the "no automatic retry after crash, requires manual toggle" recovery behavior in `dumpsys accessibility`; MIUI's Autostart/Battery-Saver/Lock-in-recents settings and their general effect; the specific `"OneKeyClean"`/`"SwipeUpClean"` `ApplicationExitInfo` description strings as known MIUI cleanup-utility signatures matching a separate app's independently reported incident.

**Hypothesis (reasoned, not directly observed in this pass):** that an active commitment does not change MIUI's kill decision (experiment #2 tests this directly, don't assume it); that the kill is exclusively cleaner/idle/battery-saver-driven rather than also occurring during ordinary active use (experiment #7 tests this).

## 6. Go/no-go recommendation and one precise Cursor follow-up task
