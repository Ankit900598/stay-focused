# Commitment Decision Evaluator + Quota Flow: Determinism Review (2026-09-27)

Research only. No files edited, no phone/Azure state touched, no secrets used, no model calls made. Findings are traced directly against: `CommitmentPolicyEvaluator.kt`, `ShortFormQuotaGate.kt`, `ShortFormQuotaStore.kt`, `AppDossierStore.kt`, `AppDossierClient.kt`, `PhoneCodexAccessibilityService.kt`, `EnforcementTraceEvaluator.kt`. Every claim below is marked **Confirmed** (read directly in this codebase), **Platform fact** (documented Android behavior, not re-derived from AOSP source in this pass), or **Unverified** (a real question this pass could not close — flagged, not guessed).

## 1. Is the evaluator truly deterministic? — Confirmed: mostly yes, with one intentional, documented side channel

`CommitmentPolicyEvaluator.evaluate(snapshot, quotaGate)` (`domain/enforcement/CommitmentPolicyEvaluator.kt:110-359`) is a pure function of its two parameters for every stage **except** the short-form quota stage. The file's own doc comment states this outright: *"The quota gate owns the daily counter, so evaluating a counted play records it; every other stage is side-effect free"* (`:102-103`). **Confirmed by reading the call:** `quotaGate.evaluate(...)` (`:221-226`) is a method on a **mutable, stateful object** (`ShortFormQuotaGate`) passed in by the caller, not a value — so `CommitmentPolicyEvaluator.evaluate` is deterministic *given* the quota gate's current internal state, but that state is itself mutated as a side effect of the call and carried forward into the next call. This is not a bug — it is the mechanism by which "1..N counted, N+1 blocked" works at all — but it means "deterministic" must be qualified precisely: **deterministic as a function of (snapshot, quota-gate-state-at-call-time), not as a function of (snapshot) alone.** Every other branch in the 250-line `when`/`if` chain (`CommitmentSnapshot`, `StudyWorldSettings`, guardrails, scope, dossier) reads only its inputs and returns a `CommitmentDecision` with no further mutation — confirmed by reading every branch; none of `ScopeGate.evaluate`, `BlankVideoTreeGate.evaluate`, `EntertainmentBanGate.evaluate`, `MediaLengthEnforcement.decideDetailed`, `StructuredSurfaceGate.evaluate`, `SurfaceEnforcementGate.evaluate` are passed a mutable object the way the quota gate is.

## 2. AppDossier resolution in the live path — Confirmed: synchronous, local-only, no network in the hot path

`CommitmentSnapshot.dossier` (`:64`) is a lazy `() -> AppDossier?`. In the live caller, `PhoneCodexAccessibilityService.inspectAndEvaluate` (`:407-465`) passes `dossier = { appDossierStore.merged(packageName, screenText) }` (`:458`). **Confirmed by reading `AppDossierStore.merged()`** (`data/AppDossierStore.kt:24-29`): it calls `AppDossier.localOnly(...)` (pure, in-memory) and `get(packageName)` — a single **synchronous SharedPreferences read**, no network I/O. `AppDossierClient.research()` (`domain/enforcement/AppDossierClient.kt:21-60`) is a genuinely blocking `HttpURLConnection` call, but it is **not** what the `dossier` lambda invokes — it is a separate mechanism (gated by `AppDossierStore.shouldResearch()`/`RESEARCH_TTL_MS`, `:38-41`) invoked from elsewhere in the service (not read in this pass — its exact call site/thread was not traced, since it is decoupled from the evaluator's hot path by construction and therefore out of scope for the evaluator's own determinism question). **Confirmed:** the evaluator itself never risks `NetworkOnMainThreadException` and never blocks on I/O beyond one SharedPreferences read. **Not a defect, but worth naming precisely:** the dossier's *stored* value can legitimately change between two `evaluate()` calls for the same package if a background research write (`AppDossierStore.put()`) lands in between — this is intentional (a dossier update should affect future decisions), not a determinism bug, but it means "same snapshot, same package, twice in a row" is only guaranteed to produce the same decision if no dossier write happened in between — a real, if narrow, precondition worth stating explicitly rather than assuming.

## 3. Quota state: read/write/persist — Confirmed: a real Ledger is wired in the live path, contradicting the in-file TODO comment

`ShortFormQuotaGate`'s own class doc says *"TODO: persist via SharedPreferences / DataStore so process death does not reset mid-day quota"* (`:51-53`) — **this comment is stale.** `PhoneCodexAccessibilityService.kt:103-104` constructs `private val shortFormQuotaGate by lazy { ShortFormQuotaGate(ledger = shortFormQuotaStore) }`, where `shortFormQuotaStore by lazy { ShortFormQuotaStore(this) }` (`:103`) **is** a real `ShortFormQuotaGate.Ledger` implementation (`data/ShortFormQuotaStore.kt:6-38`) backed by a dedicated `SharedPreferences` file (`"phonecodex_short_form_quota"`). So persistence is not a TODO in the live path — it exists and is wired — but the in-file comment should be corrected or the persistence guarantees it actually provides (§5-6 below) should be documented in its place, since the comment as written actively misleads a future reader into believing there is no persistence at all.

**Read/hydrate path (`ShortFormQuotaGate.kt:265-272`):** `hydrate(dayKey)` calls `ledger?.load(dayKey)` **exactly once per `dayKey` per gate instance** (guarded by `hydratedKeys`, a `mutableSetOf<String>`). Since the gate is a `by lazy` singleton for the service's lifetime, this means: within one process's lifetime, the ledger is read from disk once per calendar day (the first `evaluate()` call after midnight triggers a fresh `hydrate` for the new `dayKey`), and every subsequent call within that day reads only the in-memory maps — **confirmed, this is correct and cheap.**

**Write/persist path (`:274-280`):** `persist(dayKey)` is called only after a play is newly counted (`:250`, inside the `ALLOW_AND_COUNT` branch) — not on every `evaluate()` call, only on state-changing ones. `ShortFormQuotaStore.save()` (`data/ShortFormQuotaStore.kt:24-29`) calls `prefs.edit().putInt(...).putString(...).apply()`.

## 4. What `SharedPreferences.apply()` guarantees, and does not — Platform fact, stated precisely because the design must not overclaim

- **Guaranteed:** the in-memory `SharedPreferences` object is updated synchronously before `.apply()` returns — a subsequent `.get*()` call on the *same* `SharedPreferences` instance within the *same* process immediately sees the new value. This is why `hydrate()`'s once-per-day-per-instance caching is safe *within a single process's lifetime* — it never needs to re-read disk to see its own writes.
- **Guaranteed:** the actual disk write is durable *if the process survives long enough for the OS to flush it* — Android schedules `.apply()`'s disk write asynchronously and, on orderly lifecycle transitions, the platform waits for pending writes to finish before allowing certain transitions to complete.
- **Not guaranteed:** durability across a **hard kill** — OOM-killer termination, `adb shell am force-stop`, a native crash, or the user force-stopping the app from Settings can all terminate the process before an in-flight `.apply()` write reaches disk. In that specific window, the in-memory count that was already reflected in a returned `ALLOW_AND_COUNT` decision can be lost from disk, and after restart `hydrate()` will load the **older**, lower persisted count.
- **Not guaranteed:** any error signal on write failure — `.apply()` returns `Unit` with no callback, no exception, and no way for `ShortFormQuotaStore.save()` to know whether the write actually landed. `save()` cannot detect or report a failed persist.
- **This report does not claim exactly-once durability, because the design does not provide it.** The correct, provable claim is: **at-least-once in-memory counting within a process's lifetime, with best-effort (not guaranteed) cross-restart durability of the *last* write before a hard kill.** Any recommendation below must not overstate this.

**Consequence, stated precisely:** a hard kill immediately after a counted play can cause that specific count (and, separately, that play's fingerprint in `signaturesByDayKey`) to be lost from disk. After restart, `hydrate()` loads the older count — the user's effective daily allowance is very slightly **more generous** than N that day (the lost play doesn't count against the limit going forward), never less generous, and never a security/adult-content-bypass issue (adult BLOCK and scope checks do not depend on the counter at all — confirmed by reading `ShortFormQuotaGate.evaluate`, `:169-181`, the adult check runs and returns before any counter read/write). This bounds the risk correctly: it is a minor product-laxity risk, not a safety bypass.

## 5. Does replay prove any of this? — Confirmed: no, replay tests a structurally different thing

`EnforcementTraceEvaluator.evaluate` (`domain/enforcement/trace/EnforcementTraceEvaluator.kt:23-54`) constructs, on **every single call**, a brand-new `ShortFormQuotaGate(ledger = SeedLedger(trace.quotaAlreadyCounted))` (`:51`) — a fresh gate, seeded from a fixture-supplied starting count, never touching the real `ShortFormQuotaStore`/`SharedPreferences` at all. This is **correct and good** for what it proves — it makes the evaluator's *decision logic* fully reproducible and isolated from any real persistence, timing, or OS behavior — but it means **replay proves nothing about `ShortFormQuotaStore`'s actual read/write correctness, `.apply()` timing, corruption handling, or cross-process-restart behavior.** Those are two independent claims (`"the law is correct given a count"` vs. `"the count itself survives real-world conditions"`), and only the first is exercised by the existing trace suite. Any exit criteria for this work (§8) must test both, separately.

## 6. Corrupted storage / read failure — Confirmed asymmetry, real robustness gap

- `AppDossierStore.decode()` (`data/AppDossierStore.kt:60-77`) wraps the entire JSON parse in `try { ... } catch (_: Exception) { null }` — a corrupted or unexpected dossier value degrades safely to "no stored dossier," not a crash.
- `ShortFormQuotaStore.load()` (`data/ShortFormQuotaStore.kt:13-22`) has **no try/catch at all** around `prefs.getInt(countKey(dayKey), 0)` / `prefs.getString(sigKey(dayKey), "")`. If the value stored under `countKey(dayKey)` were ever not an `Int` (a type-mismatch corruption — implausible from this store's own code today, since it is the sole writer of this dedicated prefs file, but not provably impossible against e.g. a future code change, a manual prefs-file edit, or a platform-level corruption), `prefs.getInt` throws `ClassCastException`, which propagates uncaught through `hydrate()` → `ShortFormQuotaGate.evaluate()` → `CommitmentPolicyEvaluator.evaluate()` → `inspectAndEvaluate()`. **Unverified in this pass:** whether `inspectAndEvaluate`'s callers (`mainHandler.post { inspectAndEvaluate(...) }` and direct calls at `PhoneCodexAccessibilityService.kt:110, 257, 265`) are wrapped in any outer try/catch — the surrounding code read in this pass shows no such wrapper at those call sites, and an uncaught exception on the main thread is fatal to the process (platform fact) — but a broader class-level or `Application`-level uncaught-exception handler was not searched for in this pass and would need to be checked before concluding this actually crashes the app in practice.
- This is a real, fixable asymmetry: `ShortFormQuotaStore.load()` should be as defensive as `AppDossierStore.decode()` already is.

## 7. Duplicate identity / 8-second dedupe / same-day signatures — Confirmed mechanism, one precise collision risk

Two independent suppression layers, **both keyed by the same `playFingerprint`** (`ShortFormQuotaGate.kt:329-343`: `"$packageName|$title|${surface.surface.name}"`, deliberately excluding duration/clocks *"a11y thrash would double-count the same play"*):
1. **`recentPlayFingerprints` + `DEDUPE_WINDOW_MS = 8_000L`** (`:183-204`): if the *same* fingerprint was seen within the last 8 seconds, the repeat play is `ALLOW_DUPLICATE` (if under limit) or `BLOCK_QUOTA_EXCEEDED` (if at/over limit) — never counted again. `pruneRecent` (`:282-285`) evicts entries older than `4 × DEDUPE_WINDOW_MS` (32s) — pure memory housekeeping, unrelated to the day-scoped dedupe below.
2. **`signaturesByDayKey`** (a `LinkedHashSet<String>` per day, `:206, 246`): once a fingerprint has been counted *at all* today, re-encountering it later the same day (well past the 8-second window — e.g., the user re-opens the same Short an hour later) is recognized via `fingerprint in signatures` (`:209`) and again returns `ALLOW_DUPLICATE`/`BLOCK_QUOTA_EXCEEDED` without incrementing the counter.

**Confirmed collision risk (under-counting, not over-counting):** because the fingerprint excludes duration and is only `packageName|title-snippet(≤80 chars)|surfaceKind`, two **genuinely different** Shorts that happen to share the same package, the same short-form surface classification, and a title snippet that collides within the first 80 characters (or both lack an extractable title, per `extractTitleHint`'s fallback at `:345-356`, which can return `null` for a nearly-blank a11y tree) would be treated as "the same play" — the second would not consume quota. This under-counts against the limit (the user gets a free extra Short that day), which is the same class of risk as §4's process-death case: a laxity risk, not a safety-bypass, since it can never turn an adult-content BLOCK into an ALLOW (that check runs earlier and independently) and can never widen scope.

## 8. Midnight / time-zone changes — Confirmed rollover mechanism, confirmed zone-capture gap

`todayKey(nowMillis)` (`:80-82`) computes `Instant.ofEpochMilli(nowMillis).atZone(zoneId).toLocalDate()` + `":short_form_video"`. Crossing local midnight naturally produces a new `dayKey` string on the next `evaluate()` call, and `hydrate()` correctly treats it as a fresh key (starting at count 0 unless the ledger has something stored for that new key, which it won't on a genuinely new day) — **confirmed correct for the ordinary midnight-rollover case.**

**Confirmed zone-capture gap:** `zoneId: ZoneId = ZoneId.systemDefault()` (`:56`) is evaluated **once**, at `ShortFormQuotaGate` construction time, which — because the gate is `by lazy` and lives for the `PhoneCodexAccessibilityService` instance's lifetime (`:104`) — means a live change to the device's time zone (flying across zones with auto-timezone on, or the user manually changing it) during an active session is **not** picked up by the already-constructed gate instance; it keeps computing `dayKey` against the zone captured at construction until the service/process restarts and `shortFormQuotaGate` is reconstructed. **Unverified in this pass:** how often/whether `PhoneCodexAccessibilityService` itself gets recreated by the OS during normal use (accessibility services can be killed and restarted by the system under memory pressure independent of user action) — if that happens somewhat routinely, this gap self-heals often in practice; if the service is unusually long-lived on a given device, the gap could persist for the life of a session. This needs a targeted phone check, not a code-only answer.

## 9. Process death — Confirmed: quota resets are bounded to "at most the last write," not "everything"

With the real `Ledger` wired (§3), process death does **not** reset the whole day's quota to zero, contradicting the stale in-file TODO comment (§3) — `hydrate()` reloads whatever was durably persisted. The precise, bounded risk is exactly §4's `.apply()` caveat: only the most recent write(s) not yet flushed to disk at the moment of a hard kill can be lost. This is a materially better state than "no persistence at all," and should be described that way rather than either overclaiming full durability or ignoring that persistence exists at all.

## 10. Races — Confirmed: single-threaded by construction for every call site found, with one caveat

Every call site of `CommitmentPolicyEvaluator.evaluate`/`inspectAndEvaluate` found in `PhoneCodexAccessibilityService.kt` (`:110, 257, 265, 2560, 2571`) is either a direct call from `onAccessibilityEvent` (which the Android platform dispatches on the service's main thread by default) or a `mainHandler.post { ... }` dispatch onto the same main `Looper`. The one background-thread path found (`classifierExecutor`, used for screenshot capture + the vision-classification network call, `:1795-1852`) does **not** touch `shortFormQuotaGate` or call the evaluator directly on that thread — it hops back via `mainHandler.post { ... }` (`:1877`) before any decision-affecting call (`applyVisionCounselResult`) runs. **Confirmed: no evidence of a cross-thread race on the quota gate or the evaluator in the code read in this pass.** **Unverified:** this conclusion depends on the platform default that `AccessibilityService.onAccessibilityEvent` runs on the main thread, which was not independently cross-checked against this app's `AndroidManifest.xml` service declaration (a non-default thread configuration, while unusual, was not ruled out by inspection in this pass) — flagged as the one remaining gap in the race analysis, closeable with a single manifest read not performed here.

## Recommended smallest safe architecture (no product-rule changes)

The current *rules* (1..N counted, N+1 blocks, adult never counts, passive never counts, dedupe within 8s and within the day, long-educational exception) are correct as specified and require **no logic change**. The gaps are entirely in **persistence robustness** and **documentation truthfulness**, not in the decision law:

1. **Make `ShortFormQuotaStore.load()` defensive**, matching `AppDossierStore.decode()`'s existing pattern: wrap the two `prefs.get*` calls in `try/catch`, treating any exception as "no stored state for this day" (`(0, emptySet())`) rather than propagating. This is the single highest-value, lowest-risk fix — it converts a theoretical crash-on-corruption into the same graceful degradation the dossier store already has, with no change to counting semantics.
2. **Correct the stale TODO comment** in `ShortFormQuotaGate.kt:51-53` to describe what's actually implemented (a real `Ledger`, wired via `ShortFormQuotaStore`/`SharedPreferences`, with `.apply()`'s documented at-most-last-write-may-be-lost-on-hard-kill caveat) — this is a documentation fix, not a code-behavior fix, but it directly prevents a future reader (or a future AI-assisted change) from acting on the false belief that no persistence exists.
3. **Do not add a stronger durability mechanism (e.g., switch to `.commit()`, or add `fsync`-level guarantees) unless product explicitly wants to shrink the "last play near a crash" laxity window** — `.commit()` is synchronous and blocks the calling thread (the main thread, per §10) on disk I/O for every single counted play, which trades a very rare, very small laxity risk for a real, guaranteed UI jank/ANR risk on every Nth short-form play. This is a worse trade for a "personal commitment OS" whose own product principles prioritize UI smoothness (`docs/CURRENT_STATE.md`'s "YouTube/Netflix/Claude-level smoothness" standard) — **recommend explicitly against this**, and note it only because it is the obvious-looking "just make it more durable" alternative that should be named and rejected, not silently ignored.
4. **Do not change the fingerprint to include duration/clocks** to "fix" the under-counting collision risk from §7 — the existing exclusion is deliberate and well-reasoned (prevents a11y-thrash double-counting, a materially worse and more common failure mode than the rare title-collision under-count). If the collision risk is judged worth addressing, the correct direction is a *longer* or *more specific* title hint (e.g., raise the 80-character cap, or incorporate a stable per-video identifier if one becomes available from a future surface-detector improvement) — not reintroducing duration into the key.
5. **Re-derive `zoneId` per `todayKey()` call instead of capturing it once at gate construction** (§8) — change `ShortFormQuotaGate`'s `zoneId` parameter from a captured value to a supplier (`() -> ZoneId = { ZoneId.systemDefault() }`), read fresh each time `todayKey()` is called. This is a small, additive, backward-compatible signature change (existing callers passing a fixed `ZoneId` — e.g. tests — keep working by passing `{ fixedZone }`) that closes the live-timezone-change gap without touching any counting logic.
6. **No change needed to the dossier resolution path** — it is already synchronous, local, and side-effect-free relative to the evaluator; the only follow-up is verifying (not fixing) whether `AppDossierClient.research()`'s trigger site is itself safely decoupled from the main thread, which is outside this evaluator's scope.
7. **No change needed to the trace/replay mechanism** — its isolation from the real ledger is correct and should stay that way; if persistence-layer correctness needs its own test coverage, that is a *new, additional* test target (§ below), not a change to how replay works today.

## Alternatives considered and rejected

- **Switching quota persistence to `.commit()`**: rejected per point 3 above — trades a rare laxity risk for a routine main-thread I/O stall.
- **Moving quota persistence off the main thread (e.g., into a coroutine/executor)**: would remove the `.commit()` jank concern if durability were later strengthened, but `.apply()` already schedules its write off the calling thread internally (platform fact) — there is no jank to remove today, so this adds complexity (a new dispatcher, a new place for the "no races" analysis in §10 to be re-verified) for no present benefit. Revisit only if point 3's rejection is later reversed by product.
- **Making the quota gate itself a value/pure-function design (no internal mutable state) with counts threaded explicitly through every call**: would make determinism trivially total (no side channel at all), but this is a larger refactor than the bug/gap actually requires — the side channel is already correctly scoped to exactly one stage, already documented, and already isolated by the trace evaluator's fresh-gate-per-call pattern. Not recommended as "smallest safe" given no defect was found in the mutation itself, only in its persistence layer's error handling.
- **Adding a session/lock (e.g., `synchronized`, a mutex) around `ShortFormQuotaGate.evaluate`**: rejected — §10 found no evidence of concurrent access in the live path; adding a lock defends against a race that isn't demonstrated to exist, adds main-thread contention risk for no proven benefit, and would need its own correctness proof. If the one unverified item in §10 (manifest thread configuration) turns up a real background-thread caller, revisit then, not preemptively.
