## Current gate (2026-10-12)

Xiaomi's normal Files installer explicitly showed Google Play Protect's sensitive-data block for the previous debug APK. Do not retry that installer, disable Play Protect, or route around the warning with ADB. A fresh read-only visit still opens Play Console's developer-account signup, not an existing console or app listing. It asks the account owner to choose “Yourself” or “An organization,” and says that the selected Google account will own the account and ownership cannot later be changed. No account type was selected; no account, app listing, upload, appeal, or phone install has been created by this work. This is a human ownership/legal choice, not an automation step.

Google's current [Internal App Sharing instructions](https://support.google.com/googleplay/android-developer/answer/9844679) allow debuggable APKs and re-sign them, but require an authorized Play Console uploader and an app selected in the Console. The current account signup state therefore prevents upload. Google's [Play Protect warning guidance](https://developers.google.com/android/play-protect/warning-dev-guidance) says sideloaded applications declaring Accessibility can be automatically blocked in select markets and directs developers to review policy/minimum permissions before appealing; do not treat disabling Play Protect or using ADB as the fix.

**Separate release policy gate:** Google's [AccessibilityService policy](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en) requires an accessibility declaration and demo for non-accessibility-tool apps, and distinguishes static human-defined rules from autonomous Accessibility decisions. Source review confirms Strlix's disclosure and consent flow, but also confirms a model classifier can trigger a BLOCK overlay under a user-confirmed `AI_DECIDE` policy. Whether that design is permitted is unresolved; get expert policy review before Play distribution. Strlix does not claim disability-tool status and must not set `isAccessibilityTool=true` to bypass the automation restriction. No internal test channel is evidence of Play policy approval.

The current Android source search found no privacy-policy/Data Safety artifact or in-app policy link. The disclosure mentions the configured backend but not the current provider or retention details. Confirm the real backend-to-model data path and retention terms, publish/review the privacy policy and Data Safety answers, then make the in-app disclosure consistent. This repository-only search cannot prove there is no separately hosted policy.

Google's [AccessibilityService policy](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en) requires a declaration and demonstration of the consent/core flow, and its [foreground-service guidance](https://support.google.com/googleplay/android-developer/answer/13392821?hl=en) requires a type declaration and demo evidence. The current cloud-classifier BLOCK path needs review against the Accessibility automation rule before release; see the issue log. The heartbeat service and subtype are present in source, so removing a permission solely to avoid Play Protect is not a valid fix. An internal test is not Play-policy approval.
3. Rebuild from the reviewed tree; verify the APK hash, generated `BuildConfig` empty secret, packaged loopback network config, and absence of reusable credentials. Do not upload the normal debug APK or any build carrying `STRLIX_BACKEND_APP_SECRET`.
4. Upload only the sanitized APK through the authorized Play Console internal-app-sharing flow and install it from the resulting Play link. Google re-signs internal-sharing uploads, so the installed hash will differ from the local APK; record the Play artifact identity instead of claiming a byte-for-byte installed hash match.
