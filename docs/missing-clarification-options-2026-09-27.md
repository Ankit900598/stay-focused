# Missing-Answer-Options Clarification Bug: Root Cause + Capability Matrix + Design (2026-09-27)

Research/design only. No files edited, no Azure/model calls made, nothing deployed, no phone touched. Evidence is from reading `backend/promiseCompilerService.js` and `app/src/main/java/com/phonecodex/app/ui/home/PromiseUnderstandingCard.kt` directly, cross-checked against the typed-scope investigation trail already on disk (`docs/v09-typed-scope-clarification-loop-2026-09-26*.md`, `docs/browser-scope-enforcement-review-2026-09-26.md`) — this bug is a **different, older mechanism**, not the v09-only typed-scope gate those reports cover; see §0.

## 0. This is a separate mechanism from the v09 typed-scope work — confirmed, not assumed

`applyScopedAppRuleGates`'s input, `scopedSplit`, is computed unconditionally at `backend/promiseCompilerService.js:3356`:
```js
const scopedSplit = splitScopedAppBlocks(mapAppRules(parsed.blockedApps, "BLOCK"));
```
with **no `promptVersion`/`scopeContractFor` check anywhere in `splitScopedAppBlocks`, `classifyAppScope`, or `applyScopedAppRuleGates`**. This runs identically under `promise_compiler_v07` and `promise_compiler_v09`. It operates on a per-app-rule **free-text `scope` string** (`blockedApps[i].scope`, e.g. `"shorts"`, `"whole app"`) — a different, older field than the top-level typed `dto.scope`/`ScopeKind` object the last three reports investigated. **This bug is not v09-specific and is not fixed by anything recommended in the prior three reports.**

## 1. Exact root cause and minimal reproducer

**Root cause, file/line exact:**

1. `classifyAppScope(raw)` (`:2208-2222`) classifies a per-app `scope` string into exactly three buckets:
   - `"whole_app"` if the trimmed, lowercased string is literally one of `WHOLE_APP_SCOPES` (`:2175-2178`) — `""`, `"all"`, `"app"`, `"whole"`, `"whole_app"`, `"whole app"`, `"entire"`, `"entire_app"`, `"entire app"`, `"full"`, `"full_app"`, `"any"`, `"everything"`.
   - `"short_form"` if it's literally one of `SHORT_FORM_APP_SCOPES` (`:2179-2183`) — `"shorts"`, `"short"`, `"reels"`, `"reel"`, `"short_form"`, `"short-form"`, `"short form"`, `"short_form_video"`, `"short-form video"`, `"short videos"`, `"short video"`, `"short_videos"`, `"short_video"`, `"spotlight"` — **or** if it contains a short-form word (`SHORT_FORM_SCOPE_WORD`, `:2202`) and does **not** also contain a whole-app claim, an exclusion word, or another named surface word.
   - `"unknown"` for everything else — **explicitly including** any string containing `EXCLUSION_SCOPE_WORD` (`except|but|besides|other than|apart from|excluding|outside`, `:2205`) or `OTHER_SURFACE_SCOPE_WORD` (`feed|home|comments?|messages?|dms?|chats?|stor(y|ies)|search|live|long|explore|brows(e|ing)|music|subscriptions?|posts?|calls?`, `:2206`).
2. `splitScopedAppBlocks` (`:2236-2264`) routes every `"unknown"`-classified rule into `unrepresentable` (`:2260`) — no `surfaceRules`/`suggestedAppRules` entry is produced for it, and critically, **no `clarificationOptions` entry is produced for it either.**
3. `applyScopedAppRuleGates` (`:2363-2403`) reads `scopedSplit.unrepresentable`; if non-empty, sets `clarificationRequired=true` (`:2390`), `canStartCommitment=false` (`:2391`), a generic `clarificationQuestion` **only if one wasn't already set** (`:2393-2395`, `"Should I block all of {label}, or only part of it (like its short videos)?"`), and a caution message (`:2396-2401`). **It never reads, writes, or checks `dto.clarificationOptions` anywhere in this function.** If nothing upstream (Google-video, shorts-scope, compound-intent — the three producers investigated in the prior reports) happened to already populate `dto.clarificationOptions` for an unrelated reason, `dto.clarificationOptions` stays `[]`.
4. Android: `PromiseUnderstandingCard.kt:126` — `if (understanding.clarificationOptions.isNotEmpty()) { ...render ClarificationOptionList... }`. When empty, the only rendered affordance besides the question text is `QuietAction("Edit promise", onEditPromise)` at `:200-205`. **There is no path from "read the question" to "answer it" other than free-typing a new promise from scratch.**

**Minimal reproducer (no model call needed — this is deterministic, testable offline):** a promise whose `blockedApps` includes an entry with `label: "Instagram"`, `packageName: "com.instagram.android"`, `scope: "messages"` (or any string containing `except`, `dm`, `feed`, `long`, etc.). `classifyAppScope("messages")` → `"unknown"` (matches `OTHER_SURFACE_SCOPE_WORD`) → `unrepresentable` → `clarificationRequired=true`, `canStartCommitment=false`, `clarificationOptions=[]`. Equally: any blockedApps entry whose model-written `scope` string is literally `"everything except shorts"` → `EXCLUSION_SCOPE_WORD` matches `"except"` → forced `"unknown"` regardless of the short-form word also present (`:2213-2220` explicitly checks exclusion **before** allowing the short-form fallback) → same dead end.

## 2. Capability matrix

| Interpretation | Representable via `classifyAppScope`'s free-text scope field (the mechanism this bug lives in)? | Representable via the typed `ScopeKind`/`EnforcementScope` schema (the v09 mechanism, if fully wired per the prior reports)? | Notes |
|---|---|---|---|
| "Only Shorts" (e.g. block YouTube Shorts, whole app otherwise fine) | **Yes** — bare `"shorts"`/`"reels"`/etc. token, or a short-form word with no whole-app/exclusion/other-surface word alongside it (`:2202-2221`) | **Yes** — `SHORT_FORM_ANY_HOST` (cross-app) exists as a preset; a single-app "Shorts only" needs the new `APP_ONLY`-with-`surfaces=[PLAYER_SHORT]` kind identified as missing in the prior report (`docs/v09-typed-scope-clarification-loop-2026-09-26-v2.md §2`) — still not shipped. | Confirmed representable at the free-text layer; confirmed **not yet** representable as a distinct single-app kind at the typed layer (same gap already documented). |
| "All of YouTube" / whole-app block | **Yes** — literal `WHOLE_APP_SCOPES` membership, or empty string (default) | **Yes** — `APP_ONLY` | Both layers handle this cleanly; this is the one unambiguous case. |
| "Everything except Shorts" (block the whole app but exempt/allow its short-form surface) | **No — proven by code, not assumed.** `EXCLUSION_SCOPE_WORD` (`"except"`) forces `"unknown"` unconditionally, checked *before* the short-form fallback logic even runs (`:2213-2220`). There is no code path in `classifyAppScope`/`splitScopedAppBlocks` that can ever emit anything other than `unrepresentable` for this phrasing. | **Not shipped, but structurally closer to possible.** The typed schema has a general `exempt` clause axis (used today by `SOCIAL_MESSAGING_ONLY`'s DM exemption and `SOCIAL_FEED_AND_REELS_ONLY`'s companion-app exemption — real, working precedent). No existing `ScopeKind` preset expresses "this app, exempting its short-form surface" (the inverse of `APP_ONLY`+shorts) — it would need a new preset row, same class of change as the missing single-app-shorts kind above, just with the include/exempt clauses swapped. | The two "except Shorts" directions (only-shorts vs. everything-but-shorts) both currently require a **new preset row** at the typed layer; neither is a same-day fix. |
| Instagram messages vs. Reels — "block Reels, keep messages" | **No.** `"dms?"`/`"messages?"`/`"chats?"` are in `OTHER_SURFACE_SCOPE_WORD` (`:2206`) — any mention forces `"unknown"`. `"reels"` alone (no message mention) *would* classify as `short_form` per the `SHORT_FORM_APP_SCOPES` set, but a promise phrased as a genuine two-sided contrast ("block Reels, keep messages") is likely to include both surface words in the same `blockedApps[i].scope` string or across two entries, triggering the exclusion/other-surface path either way. | **Yes, already shipped as a named preset.** `SOCIAL_FEED_AND_REELS_ONLY` (`ScopeKindPresets.kt:171-195`, backend `:566-575`) is exactly "feed + Reels in scope, with an optional companion-app (Messenger-style) exemption." This is the one example in this matrix where the typed schema is *already ahead of* the free-text mechanism. | This is strong evidence that fixing this bug should route toward "produce typed scope options," not toward "patch the free-text classifier" — the typed side already has the right shape for this exact example. |
| Instagram messages *only* (block feed+Reels, exempt DMs) | **No** (same as above — `messages`/`dms` triggers `unknown`) | **Yes** — `SOCIAL_MESSAGING_ONLY` with its DM/thread exempt clause (`ScopeKindPresets.kt:150-169`) | Same conclusion as above. |
| "Long videos only" / "everything except long-form" (the mirror of the Shorts case, e.g. block movies/long OTT but not short clips) | **No** — `"long"` is explicitly in `OTHER_SURFACE_SCOPE_WORD` (`:2206`), forces `unknown` | **No preset today.** No `ScopeKind` expresses "long-form surface only" or "any-surface-except-long-form" for a single app or cross-app. | Genuinely unrepresentable at both layers today — would need new preset work, not just a bridge. |
| Any promise combining two+ of the above in one sentence (e.g. "block Instagram feed and Reels but not messages, and block all of Facebook") | **No**, compounds the same-app failure per clause | **Only via composition** — multiple typed scope objects (one per app/clause), which is exactly what the separately-tracked compound-intent clarification (`inferCompoundIntentClarification`) already exists to disambiguate at the *promise* level, though not at the *single-app-multi-surface* level this bug is about | Composition here means "resolve app-by-app, surface-by-surface," not a single unified scope object — consistent with the schema's own "five orthogonal axes" design principle already documented in `docs/scope-semantics-v1.md`. |

**Bottom line for the matrix:** the free-text `classifyAppScope` mechanism this bug lives in can express strictly less than the typed schema already can. Every case that mechanism marks `unrepresentable` either (a) already has a working typed-schema answer (Instagram messages/Reels) that just isn't being offered as a clarification option, or (b) needs one new preset row at the typed layer (Shorts-only / except-Shorts for a single app) that was already identified as missing in the prior report, or (c) is genuinely unrepresentable today at both layers (long-form-only/except-long-form) and requires new design work, not just wiring.

## 3. Safe clarification design

**When to produce 2-3 selectable choices vs. "no safe choice exists":**
- If `scopedSplit.unrepresentable` contains a rule whose free-text `scope` maps to a **known, already-typed-schema-representable pattern** (per the matrix above — e.g. contains a message/DM word for a social app with a known `SOCIAL_MESSAGING_ONLY`/`SOCIAL_FEED_AND_REELS_ONLY` preset, or a shorts word alongside a whole-app/exclusion word for an app where a single-app-shorts preset exists once built), **produce exactly the 2-3 concrete options the existing UX contract calls for**, each carrying its own typed scope (reusing the exact carry/snapshot/verification and bridge-provenance machinery already designed in the three prior reports — do not reinvent it here). Example phrasing for Instagram:
  - *"You mentioned Instagram messages and Reels. What should this promise cover?"*
    - A: "Just the Reels/feed — messages stay open" (→ `SOCIAL_FEED_AND_REELS_ONLY`, exempt Messenger-style DM surface)
    - B: "Just messages — Reels/feed stay open" (→ `SOCIAL_MESSAGING_ONLY`)
    - C: "All of Instagram" (→ `APP_ONLY`)
- If the free-text scope maps to a pattern with **no typed-schema representation at all** (e.g. "long videos only," "everything except long-form") — **do not silently degrade to a partial or generic option.** Set `clarificationRequired=true`, `canStartCommitment=false`, `clarificationOptions=[]` **as today**, but change the copy: the current generic question (`"Should I block all of {label}, or only part of it (like its short videos)?"`, `:2394`) is itself misleading when "part of it" isn't actually offerable — replace it with an explicit statement that this exact distinction isn't supported yet, plus a concrete rewording suggestion ("Try naming it as 'all of {label}' or 'just {label}'s short videos' — I can't yet target long-form video specifically"). This directly satisfies "how the user can reword instead" without inventing a fake choice.
- **No silent defaults, ever, in either branch.** Both branches keep `canStartCommitment=false` until the user acts — the only difference is whether "acts" means "taps a real option with a verified typed scope" or "edits the promise text into a phrasing the system can actually represent." Start must remain disabled until the user has both selected (if options exist) and seen the recomputed preview reflecting that exact selection — reuse the existing `canStartCommitment` recompute-after-pick flow from the typed-scope work rather than a new one.

**Never route an unrepresentable case to a broader BLOCK or a weaker ALLOW.** Concretely: `applyScopedAppRuleGates` must remain a Start-closing-only gate (it already is, per its own doc comment `:2360-2361`, "Final gate... Only ever closes Start; never reopens it and never rewrites an action into a weaker one" — this property must be preserved, not just documented, when clarification options are added). The fix in this design adds *options*, not a fallback resolution — if the user never picks and never rewords, the promise simply never starts, which is the correct fail-closed outcome, not a defect to "fix away."

## 4. Trust/security requirements

This must reuse — not duplicate or weaken — the machinery already designed across the three prior reports:
- **Options must be server-validated and tied to the unchanged promise and displayed snapshot.** Any new clarification options this fix produces (per §3's first branch) must go through the exact same snapshot-carry-verification gate designed in `docs/v09-typed-scope-security-addendum-2026-09-26.md §2` before a pick is honored — including the "no anchor supplied = fail closed" rule, the promise-text-unchanged check, and the duplicate/stale/mismatched-id fail-closed cases.
- **Reject forged/stale/mismatched choices** using the same re-derivation-based provenance check from the addendum's §3: since the new options this fix would add (per §3 above) are themselves deterministic functions of the `blockedApps` entries' free-text `scope` strings, the same "re-run the deterministic builder against the verified-unchanged promise/app-rule state and compare" pattern applies directly — no new trust mechanism needs to be invented.
- **Never turn an unrepresentable scope into a broader BLOCK or weaker ALLOW** — stated explicitly here because it is the one property this specific bug's *symptom* (stuck, no options) is accidentally protecting today; any fix must not accidentally trade "stuck but safe" for "unstuck but silently wrong." A rushed fix that, say, defaults an unresolvable per-app scope to `"whole_app"` (to unblock the user) would violate this directly and must not be done — the correct unblock is *always* either a verified real option or a reworded promise, never a guessed default.

## 5. Implementation plan by file/layer

**Backend:**
- `backend/promiseCompilerService.js`, near `classifyAppScope`/`splitScopedAppBlocks` (`:2208-2264`): add a **recognizer, not a resolver** — a small, explicit, allowlisted set of "known-but-not-bare" patterns (message/DM word for a `SOCIAL_MESSAGING_ONLY`-eligible app, shorts word for a to-be-built single-app-shorts kind) that, instead of falling into `unrepresentable`, produce a small set of candidate typed-scope objects (reusing `ScopeKindPresets`/`expandScopePreset`-equivalent construction, per the naming/allowlist discipline from the prior reports — not free-text-derived, deterministically built from the recognized pattern).
- `applyScopedAppRuleGates` (`:2363-2403`): when `scopedSplit.unrepresentable` entries are all "recognized-but-needs-a-pick" (per the new recognizer), populate `dto.clarificationOptions` with the 2-3 candidates instead of leaving it empty; when an entry is genuinely unrecognized, keep `clarificationOptions=[]` but rewrite `clarificationQuestion`/`cautionMessages` per §3's honest-rewording copy.
- New allowlist table analogous to the six-entry table in `docs/v09-typed-scope-security-addendum-2026-09-26.md §3` — do not reuse that exact table (different producer family), but follow the same "explicit allowlist, re-derivable, never AI-prose-sourced" discipline.

**Android:**
- `app/src/main/java/com/phonecodex/app/ui/home/PromiseUnderstandingCard.kt`: no structural change needed for the "options now populated" branch — `ClarificationOptionList` already renders whenever `clarificationOptions` is non-empty (`:126-138`). For the "still empty, but now honestly worded" branch, verify the question-text rendering path (elsewhere in this file, not read in this pass) doesn't need its own copy change beyond what the backend now sends — confirm before assuming no Android change is needed.
- Confirm `PromiseClarificationLaw`/`buildPromiseUnderstanding` (from earlier investigation sessions) don't have their own independent "must have options or treat as a different state" branching that would need updating in parallel — not verified in this pass, flagged as a required check before implementation.

## 7. Are prompt changes needed, or are deterministic server-side options preferable? Keep YouTube-specific logic out.

**Deterministic server-side options are clearly preferable here, and no prompt change is required for the core fix.** The bug is not about the model failing to say the right thing — it's about a deterministic classifier (`classifyAppScope`, pure regex/set logic, zero model involvement) routing recognized-but-ambiguous patterns into a dead end instead of into a small set of pre-built typed candidates. Everything in §5's plan is achievable by extending that same deterministic classifier and reusing existing, already-shipped typed presets (`SOCIAL_MESSAGING_ONLY`, `SOCIAL_FEED_AND_REELS_ONLY`) — no model call, no prompt wording, is needed to fix the Instagram-messages-vs-Reels case, because the classifier and the presets are both pure code today.

A prompt change would only become relevant if the fix instead relied on the *model itself* recognizing "the user meant messages vs. Reels" and emitting a typed scope directly in its own output — which would reintroduce exactly the "AI prose is load-bearing for scope" risk the whole typed-scope redesign exists to eliminate, and the provenance-forgery risk documented in the security addendum. **Recommend explicitly against a prompt-based fix for this bug.**

**Keep YouTube-specific logic out — confirmed achievable, since none of §5's plan is YouTube-specific.** `MIXED_SURFACE_PACKAGES` (`:2185-2192`) already lists YouTube alongside Instagram, Facebook, Snapchat, Chrome, and NewPipe as a flat set — the fix should extend that same general, package-agnostic pattern-recognition table, not add a YouTube branch.

## 8. Smallest safe next implementation task, and what needs product approval

**Smallest safe next task:** implement §5's backend recognizer + `applyScopedAppRuleGates` wiring for exactly the **Instagram/Facebook messages-vs-feed-vs-Reels** family (the one case in the capability matrix where the typed schema already has both needed presets shipped and tested — `SOCIAL_MESSAGING_ONLY`, `SOCIAL_FEED_AND_REELS_ONLY`). This requires zero new `ScopeKind` values, zero prompt changes, and directly closes the reported UX dead-end for a real, representable case, cleanly separable from the still-missing single-app-shorts preset work already queued from the prior report.

**Needs product approval before implementation, not just engineering judgment:**
1. **Exact plain-language wording of the 2-3 option cards** for the messages-vs-Reels family (§3's example phrasing is a draft, not a final copy decision).
2. **What to do for the genuinely-unrepresentable cases** (long-form-only, everything-except-shorts) in the interim — whether the honest "I can't yet target this" copy is acceptable product experience, or whether product wants those cases prioritized for new preset work before this fix ships at all, rather than shipping the honest-refusal copy as a temporary state.
3. **Ordering/precedence when this bug's mechanism and the three typed-scope clarification producers from the prior reports both fire on the same request** (regression matrix row 10) — this is a real product decision (which ambiguity gets asked about first, or whether both get merged into one combined ask) that this report does not resolve, since it depends on how frequently that overlap actually occurs in real user language, which needs the AI Lab's messy-language evals rather than this backend/Android trace.
